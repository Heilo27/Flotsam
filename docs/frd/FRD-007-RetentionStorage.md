# FRD-007 — Retention and Storage

**Status:** Draft · 2026-11-16 · Constitution: [TRUTHS.md](../TRUTHS.md) · PRD: [PRD.md](../PRD.md) (feature F7) · Errors: [FRD-000](FRD-000-ErrorSystem.md)
**Owns:** the data folder, the SQLite schema (single definition), the blob store, the ingest pipeline and its limits, the image pipeline and thumbnails, retention and image-budget eviction, retention exemptions, Clear history, capture modes, integrity and recovery, deletion, the search index and query layer, migrations.
**Does not own:** what is captured and how it is classified or deduplicated ([FRD-001](FRD-001-Capture.md) FR-001-05 to -15); screenshot detection ([FRD-002](FRD-002-ScreenshotPickup.md)); panel behaviour ([FRD-003](FRD-003-Library.md)); the meaning of pin, tag, note, edit ([FRD-004](FRD-004-Organize.md)); hotkey and trigger grammar ([FRD-005](FRD-005-ShortcutsTriggers.md)); settings screens and the settings registry ([FRD-008](FRD-008-OnboardingSettings.md)); error catalogue ([FRD-000](FRD-000-ErrorSystem.md)).

## Truth Test
- Serves: P1 — "anything you copied or screenshotted in the past 30 days is back": the default retention is 30 days and nothing inside it is evicted by default (image budget aside, FR-007-08); the store is local-only, so "none of it ever leaves the Mac" holds by construction (no network code exists in this module).
- Supports: S2 — bundles and screenshots are stored as first-class items (bundle members, owned screenshot copies). S4 — items with a hotkey or trigger are exempt from retention, so saved snippets never expire.
- Violates: none. Storage is local files only (A1: no sync, no account); no telemetry or usage counters leave the device (A4). `pasteCount`, `copyCount` and `lastUsedAt` are local sort and display fields only.
- Verdict: KEEP. Capture modes (Paused, Curated) and Clear history are included because they serve the "none of it ever leaves / you control what is kept" half of P1 for a tool that records everything copied; Curated mode is the smallest feature that makes the tool usable by people who will not accept automatic capture. Both are small and cuttable without touching any other FRD's core path.

## 1. Purpose
Persist every item durably and cheaply, keep the library inside the user's chosen age and disk limits without ever deleting something the user has marked as valuable, and make deleting things truly delete them.

## 2. User Stories
- As a user, I copy something and it is safely in history even if the app is killed a second later.
- As a user, I keep 30 days by default and can change it to 7 days, 90 days, 1 year or forever.
- As a user, items I pinned or gave a shortcut never disappear on their own.
- As a screenshot-heavy user, I cap image storage so history cannot fill my disk, and choose to store smaller copies of large screenshots.
- As a user who just copied a secret by mistake, I clear the last hour of history and it is really gone.
- As a privacy-minded user, I pause capture before a sensitive task, or only save clips I explicitly choose.
- As a user, if the database is damaged or a migration fails, I am told plainly and my data is never silently destroyed.

## 3. Functional Requirements

**Folder, database, schema**
- **FR-007-01** Data folder. All persistent data lives under `~/Library/Application Support/Flotsam/`, created on first launch with permissions `0700` (files `0600`). Layout: `flotsam.sqlite` (with `-wal` and `-shm`), `blobs/` (original representation files), `thumbs/` (derived thumbnails, regenerable, excluded from backups), `tmp/` (in-flight writes, emptied at launch), `corrupt-<timestamp>/` (FR-007-13), `pre-migration/` (FR-007-17). Settings are not stored here (they live in the settings registry, FRD-008). The app never writes outside this folder except: pasteboard writes, Finder drag-outs, and the diagnostics copy. Failure to create or open the folder → `STO-IO-002` (Fatal). A runtime write failure to it → `STO-IO-001`.
- **FR-007-02** Database configuration. One SQLite database, WAL journal, `synchronous=NORMAL`, `foreign_keys=ON`, `secure_delete=ON`, `busy_timeout` 5 s. Exactly one serial writer; any number of concurrent readers. All writes are transactions (FRD-004 FR-004-14 builds on this). Reads from the main thread are never performed. The SQLite binding library is an architecture decision (ADR), not a requirement; whichever is chosen is the only module that imports SQLite, and no SQLite type crosses its API (FR-000-02).
- **FR-007-03** Schema (single definition; other FRDs name fields, this FRD owns their storage). Times are UTC milliseconds since epoch.
  - `item`: `id` (UUID text, primary key); `kind` (FRD-001 FR-001-08 enumeration); `createdAt`; `lastCopiedAt` (sort key for Recent); `copyCount` (default 1; incremented by dedupe bumps); `pasteCount` (default 0); `lastUsedAt` (null until first paste or drag-out); `contentKey` (FRD-001 FR-001-15; indexed, not unique, because FRD-004 FR-004-08 allows duplicates after an edit); `plainText` (null for non-text kinds); `searchText` (FR-007-18); `sourceBundleId` (null for "Another device" and Unknown), `sourceName`; `byteSize` (sum of stored representation sizes, excluding thumbnails); `pixelWidth`, `pixelHeight` (images and screenshots); `originalPath` (screenshots only; FRD-002 FR-002-09); `pinned` (default 0); `note` (null or ≤ 2,000 characters); `updatedAt`; `hotkeyCode`, `hotkeyModifiers` (both null when none; unique index on the pair where not null); `trigger` (null when none; unique index, case-insensitive collation, where not null); `exemptReleasedAt` (FR-007-10).
  - `representation`: `id`, `itemId` (cascade delete), `uti` (e.g. `public.rtf`), `byteSize`, `blobName`. Plain text is never a representation (it is `item.plainText`); rich text and image bytes are always files in the blob store, so the database stays small.
  - `bundleMember`: `itemId` (cascade), `ordinal`, `path`, `bookmark` (blob), `isDirectory`. Files are stored by reference only (FRD-001 FR-001-12).
  - `tag`: `id`, `name` (unique, case-insensitive), `color`, `createdAt`. `itemTag`: `itemId`, `tagId` (both cascade; unique pair). Deleting an item removes its `itemTag` rows; deleting all items never deletes tags.
  - `meta`: `key` (primary key), `value`. Keys: `schemaVersion`, `screenshots.lastScanAt` (FRD-002 FR-002-08), `retention.lastSweepAt`, `budget.lastNoticeAt`.
  - An item is **exempt** (FR-007-10) when `pinned = 1` or `trigger` is not null or `hotkeyCode` is not null. This is derived, never stored as a second flag.
- **FR-007-04** Blob store. A representation file is `blobs/<first two characters of itemId>/<itemId>.<n>`. A blob is written to `tmp/`, flushed, and atomically renamed before the database transaction that references it begins; if the transaction fails the blob is removed. A blob is never modified in place. Files are removed only after the transaction that unreferences them commits. A crash between blob write and commit leaves an orphan blob that FR-007-13 reconciles. No blob is ever shared between items.

**Ingest**
- **FR-007-05** Ingest pipeline (the only way an item is created or bumped). Input: an immutable value from capture (`CapturedPayload`, FRD-001 FR-001-17), screenshot import (FRD-002 FR-002-09; supplies `createdAt`, `lastCopiedAt`, `originalPath`) or a Shelf drop (FRD-006 FR-006-13). It runs on one serial background actor, in this order: (1) inside one write transaction look up `contentKey`; a match bumps the existing item (`lastCopiedAt` = now, or the supplied date for screenshots but never moving it backwards; `copyCount` + 1) and returns `bumped(id)` with nothing else changed. (2) Otherwise apply limits (FR-007-06). (3) Disk guard (FR-007-14). (4) For images, the image pipeline (FR-007-07). (5) Write blobs (FR-007-04). (6) Insert `item`, `representation`, `bundleMember` and `searchText` in the same transaction as step 1 (so two identical payloads arriving together create one item). (7) After commit, publish an `itemsChanged` event (Library, Shelf and counts refresh; FRD-004 FR-004-13), enqueue thumbnail work, and run the budget check (FR-007-08). Result: `Result<IngestOutcome, FlotsamError>` where `IngestOutcome` is `created(id)` or `bumped(id)`. Ingest is idempotent per payload. A database or disk failure rolls back everything, removes new blobs, and returns the `STO-*` code; capture surfaces it as `CAP-IO-001` with the `STO-*` code as underlying error (one Notice, not two); screenshot import and Shelf drop surface the `STO-*` code per FRD-002 and FRD-006.
- **FR-007-06** Ingest limits (single definition of every ceiling). Plain text: 10 MiB of UTF-8. Each rich representation (`public.rtf`, `public.html`): 5 MiB. Image: 100 MiB of source bytes. Bundle: 500 members (extra members dropped, `CAP-LIM-003`). Breaches: plain text or image → the item is skipped (`CAP-LIM-001`, `SSP-LIM-001`, `SHF-LIM-001` by source); a rich representation → dropped alone and plain text kept (`CAP-LIM-002`). `{limit}` in messages is the ceiling formatted with binary units (for example "10 MB"). The ceilings are constants in one place in the code and are not user-settable.
- **FR-007-07** Image pipeline. Decoding and downscaling use ImageIO only, off the main thread, with one image in flight. Steps: (1) decode metadata; undecodable → `CAP-VAL-001` or `SSP-VAL-001` by source; (2) decode the pixel size; (3) TIFF is converted to lossless PNG; PNG and JPEG are otherwise stored as received; (4) apply the image quality preset (FR-007-08): `Balanced` and `Efficient` downscale, `Efficient` also converts opaque images to JPEG, `Original` stores as received; (5) store, and record `pixelWidth` and `pixelHeight` as the dimensions of the stored blob after any downscale (the copied original's size is not kept); (6) generate a thumbnail asynchronously: longest edge 256 px (512 px for the Library preview pane), JPEG quality 0.8, written to `thumbs/<itemId>-<size>.jpg`. A missing or corrupt thumbnail is regenerated on demand and never an error. `contentKey` always comes from the raw received bytes before any conversion or downscale (FRD-001 FR-001-15), so dedupe is unaffected by the preset. The in-memory thumbnail cache is capped at 64 MB (least recently used) and is shared by the Library (FRD-003 FR-003-13) and the Shelf (FRD-006 FR-006-07).
- **FR-007-08** Image budget and quality (settings keys `storage.imageBudget`, `storage.imageQuality`; registry in FRD-008). The budget counts the `byteSize` of stored image and screenshot representations only (not thumbnails, text, or files held by reference). Budget values: 500 MiB, 2 GiB (default), 10 GiB, Unlimited. Quality presets: **Original** (default; stored as received, TIFF as PNG), **Balanced** (longest edge above 3840 px is downscaled to 3840 px), **Efficient** (longest edge above 2560 px is downscaled to 2560 px). A downscaled image keeps its format, except an opaque PNG or TIFF that was downscaled is re-encoded as JPEG quality 0.85. Under **Efficient** every opaque PNG or TIFF is stored as JPEG quality 0.85 whether or not it needed downscaling; an image with transparency stays PNG under every preset (a TIFF becomes PNG first, then this rule applies); a JPEG is re-encoded only when downscaled. The preset applies to new items only; existing items are never re-encoded. Enforcement: after each image ingest and in each retention sweep (FR-007-09), if the total exceeds the budget, non-exempt image and screenshot items are deleted oldest `lastCopiedAt` first until the total is at or below 90 % of the budget; the item just ingested is not evicted in its own pass. Eviction honours the same 24 h `exemptReleasedAt` grace as the time sweep (FR-007-09, FR-007-10): an item un-pinned (or stripped of its last trigger or hotkey) less than 24 h ago is not evicted yet. If exempt items (including those inside the grace) alone exceed the budget, nothing exempt is evicted and `STO-LIM-001` is raised as a Notice, at most once per 24 h (`budget.lastNoticeAt`). Lowering the budget triggers the budget confirmation in FR-007-09 (its own string, with count and size). Evictions are logged as `STO-POL-001` (counts only).

**Retention**
- **FR-007-09** Retention presets and sweep (key `storage.retention`). Values: 7 days, 30 days (default), 90 days, 1 year, Forever. An item is eligible for retention deletion when it is not exempt (FR-007-10), `lastCopiedAt` is older than the preset (so re-copying an old item renews it), and `exemptReleasedAt` is null or older than 24 h. The sweep runs 30 s after launch, then every hour, and on wake from sleep; it deletes in batches of at most 500 items per transaction (so the writer is never held for more than 50 ms), through the deletion operation (FR-007-15), measured by one `retention.sweep` signpost interval covering the whole sweep, with each batch an event inside that interval. A sweep that removed rows logs `STO-POL-001` (counts only, no content) and does not raise a Notice. Changing to a shorter preset first shows a confirmation with the exact number of items that would be deleted (`storage.confirm.shorten`: "This permanently deletes {n} items older than {period}. Pinned items and items with a shortcut are kept."). Lowering the image budget has its own confirmation (`storage.confirm.lowerBudget`: "Lowering the image budget removes {count} older images ({size}). Pinned and shortcut items are kept."), not the shorten string. The core returns the count and stored size (`retentionPreview`, `imageBudgetEvictionPreview`); the strings live in the UI layer (FRD-008). When the count is 0 no confirmation is shown and the setting is applied directly. Cancel reverts the control; the sweep for the new value runs only after confirmation. Changing to a longer preset deletes nothing. Forever disables the time sweep only; the image budget still applies.
- **FR-007-10** Retention exemptions (single definition). An item with `pinned = 1`, or a trigger, or a hotkey is exempt from: the time sweep (FR-007-09), the budget eviction (FR-007-08) and Clear history (FR-007-11) unless its explicit "also delete pinned and shortcut items" option is chosen. It is never exempt from an explicit delete by the user (FRD-004 FR-004-09). When the last exemption is removed (unpin, remove trigger, remove hotkey), `exemptReleasedAt` is set to now, so a long-pinned old item is not deleted within 24 h of unpinning; it is cleared whenever an exemption is set again. The grace protects against the automatic passes (time sweep and budget eviction); Clear history (FR-007-11) honours only exemption itself, because it is the user's explicit, counted action. Exemption does not apply to files on disk: files held by reference are outside Flotsam's control.
- **FR-007-11** Clear history. Settings › Storage › "Clear History…" opens a sheet with a range (Last hour, Last 24 hours, All time) and an unchecked option "Also delete pinned and shortcut items". It shows the exact count to be deleted and a destructive "Delete {n} Items" button (`storage.confirm.clear`: "This permanently deletes {n} items. This can't be undone."). When no item is in the range (count 0) the Delete button is disabled and the secondary text reads "Nothing to clear in this range."; nothing is deleted and there is no confirmation. The core returns the count and stored size (`clearHistoryPreview`) and the number actually deleted; the strings live in the UI layer (FRD-008). Deletion uses FR-007-15 over items whose `lastCopiedAt` is inside the range, minus exempt items unless the option is checked. Tags are kept. `screenshots.lastScanAt` is not reset, so cleared screenshots are not re-imported. After the transaction the database is checkpointed (`wal_checkpoint(TRUNCATE)`) and its free pages released (`incremental_vacuum`) so deleted content is not left in the file; with `secure_delete` on (FR-007-02) deleted pages are overwritten. Clear history never touches files held by reference or screenshot originals on disk. A progress state is shown for more than 1 s of work. The result is announced with a HUD "{n} items deleted".

**Capture modes**
- **FR-007-12** Capture modes (key `capture.mode`, persisted across launches): **Active** (default), **Paused**, **Curated**. Paused: nothing is captured or saved automatically, including screenshot pickup (the pickup advances `screenshots.lastScanAt` without importing, so screenshots taken during a pause are not imported on resume). Curated: nothing is saved unless the user runs Save Clipboard (FRD-005 FR-005-06) or drops onto the Shelf (FRD-006 FR-006-13); screenshot pickup behaves as in Paused. Active resumes all capture. Save Clipboard and Shelf drops work in every mode. Changing mode takes effect within 1 poll interval (FRD-001 FR-001-01), never discards held clipboard state, and is shown at all times by the menu-bar icon (FRD-008). The mode is changed from the menu bar ("Pause Capture" / "Resume Capture") and from Settings › Storage; Curated is chosen in Settings only. The menu item reads "Resume Capture" only while Paused (and returns to Active); in Active and Curated it reads "Pause Capture" (and pauses). Paused persists across relaunch, because forgetting to resume would silently lose history only if no indicator existed; the icon state and the menu label are that indicator.

**Reliability**
- **FR-007-13** Integrity and recovery. At launch, after migration, run `PRAGMA quick_check` off the main thread. On failure, or when SQLite reports the file is damaged or not a database: move `flotsam.sqlite*` and `blobs/` into `corrupt-<timestamp>/`, create a fresh database, raise `STO-DB-002` (Notice with "Reveal Data Folder" in the Notice detail, FRD-008), and never delete the moved data. Reconcile (at launch, and weekly): (a) a blob file with no representation row and older than 10 minutes is deleted; (b) a representation row whose blob is missing is removed, and if the item then has no plain text, no remaining representation and is not a files kind (file, folder or bundle), the item is removed through the single deletion path (FR-007-15); each repair logs `STO-IO-003` with ids and counts only. A thumbnail with no item is deleted silently. Only files named as Flotsam names its blobs and thumbnails are ever judged orphans; anything else in `blobs/` or `thumbs/` is left alone. If any part of `blobs/` cannot be read (a folder cannot be listed, or a listed file cannot be inspected), the missing-blob repair (b) is skipped for that run and a file that cannot be inspected is never judged an orphan, so an unreadable folder can never empty the library. Reconcile runs off the main thread, 15 s after launch and then every 7 days, and never blocks the UI.
- **FR-007-14** Disk guard. Before writing any blob, if available capacity (`volumeAvailableCapacityForImportantUsage`) is below 500 MiB, image ingest is skipped with `STO-LIM-002` (Notice, throttled by FR-000-08); text and files still ingest until capacity is below 50 MiB, after which every ingest fails with `STO-IO-001`. SQLite "disk full" on write is `STO-DB-001`.
- **FR-007-15** Deletion (the only deletion path: user delete, retention, budget, Clear history, ungroup's bundle removal, `LIB-IO-001`, Shelf and Library delete). `delete(ids)` runs one transaction that removes the item rows and, by cascade, representations, bundle members and tag links; after commit it removes blob files and thumbnails, evicts the thumbnail cache entries, and publishes `itemsDeleted(ids)` synchronously so the hotkey registry and trigger snapshot drop the item before the call returns (FRD-005 FR-005-22). A blob that cannot be removed after commit is left for reconcile and logged as `STO-IO-003`; the delete itself still succeeds. A failed transaction deletes nothing (`STO-DB-001`). `delete(ids)` is unconditional: an explicit user delete is never refused for exemption, and FRD-003 decides whether a failed item is deleted. The automatic passes (time sweep, budget eviction, Clear history) choose their ids in a read, so their delete re-applies the selection predicate, including exemption, inside the same transaction: an item pinned, given a trigger or hotkey, or copied again since the read is skipped, never deleted. Deletion never touches a file referenced by a `file`, `folder` or `bundle` item, nor a screenshot's original.
- **FR-007-16** Performance. Measured in a release build against a 10,000-item database with 2,000 images: database open and schema check ≤ 300 ms; persist and queryable, thumbnail excluded, per FRD-001 FR-001-20 (`capture.persist`); one retention batch holds the writer ≤ 50 ms p95 (`retention.sweep`); Clear history of 10,000 items completes ≤ 5 s (`retention.clearHistory`: one interval covering the count, every delete batch and the database scrub); resident memory including a full thumbnail cache stays under the 150 MB budget set in the PRD.
- **FR-007-17** Migrations. `PRAGMA user_version` is the schema version (mirrored in `meta.schemaVersion`). Migrations are forward-only, numbered, and each runs in one transaction. Before any migration, `flotsam.sqlite` is copied to `pre-migration/flotsam-v<from>.sqlite` (only the latest copy is kept: older copies are deleted only if their names are exactly `flotsam-v<int>.sqlite`, or that name plus `-wal` or `-shm`, i.e. files Flotsam created; any other file in `pre-migration/` is never touched). A migration failure, or a database whose version is newer than the app understands, aborts startup with `STO-DB-003` (Fatal); the database is left untouched. Version 1 is the schema in FR-007-03.

**Search index and query layer**
- **FR-007-18** Query layer and search index. All reads go through one query layer that takes a filter (FRD-004 FR-004-10), search tokens (FRD-003 FR-003-09), and a sort (FRD-004 FR-004-12) and returns pages of 200 rows plus a count; sidebar counts are computed by the same filter semantics. `item.searchText` is a normalised (case-folded, diacritic-stripped) concatenation of the fields listed in FRD-003 FR-003-09 (plain text first 10,000 characters, link URL, note, tag names, source name, file and folder names of members, kind label, original file name), rewritten in the same transaction whenever any of them changes. The matching strategy (FTS5 trigram index versus an in-memory scan of `searchText`) is chosen by spike S-1 against FRD-003 FR-003-10 (p95 ≤ 100 ms at 10,000 items); whichever is chosen, results are exactly those defined by FR-003-09 (substring, AND over tokens). Until S-1 decides, the shipped strategy is the in-memory-style scan (`instr` over `searchText`, one AND per token), which already gives the FR-003-09 set; the public API is unchanged by the outcome. Rows carry the FR-003-07 primary line, and the alphabetical sort (FR-004-12) orders by that same text, locale-aware, ties broken by `lastCopiedAt` descending then `id`; every other sort ends the same way so order is stable across loads. The source-app filter and the sidebar's app counts group by one key: bundle identifier, else the "Another device" bucket (stored source name `Another device`, FR-001-14), else Unknown (FR-001-13). A page and its count are read in one transaction. Database read failure → `STO-DB-004`.

## 4. Data Requirements
- Settings keys owned here (registry in FRD-008): `storage.retention` (enum, default `d30`), `storage.imageBudget` (enum, default `gib2`), `storage.imageQuality` (enum, default `original`), `capture.mode` (enum, default `active`).
- Persisted: everything in FR-007-03 and the blob store. Not persisted: thumbnail cache, query pages, ingest queue.
- Item counts, byte sizes of database and blobs, preset values are the only storage facts appearing in diagnostics (FR-000-14); never content.

## 5. Business Rules
- Retention age is measured from `lastCopiedAt`, not `createdAt`. A re-copy renews an item; opening, pasting or editing does not.
- Exempt means pinned, triggered or hotkeyed (FR-007-10). Only an explicit delete or the Clear history option removes an exempt item.
- Bytes of files held by reference are never counted and never deleted.
- Dedupe is global and age-independent (FRD-001 FR-001-15): a retention-deleted item does not block re-capture because it no longer exists.
- Every path that creates items goes through FR-007-05; every path that removes items goes through FR-007-15.
- Nothing here makes a network call. The module has no networking imports.

## 6. Error States (codes in FRD-000 §7)
| Condition | Code | Behaviour |
|---|---|---|
| Write failed, transaction rolled back, disk full | STO-DB-001 | rolled back; surfaced per FR-000-08 |
| Database damaged | STO-DB-002 | moved aside, fresh database; Notice |
| Migration failed or version newer than app | STO-DB-003 | Fatal alert; data untouched |
| Read failed | STO-DB-004 | propagate; inline Retry in Library |
| Data folder not writable at runtime | STO-IO-001 | operation aborted |
| Data folder cannot be created or opened at launch | STO-IO-002 | Fatal; "Reveal Data Folder" and "Quit" |
| Orphan or missing blob repaired | STO-IO-003 | Info, logged |
| Exempt items alone exceed image budget | STO-LIM-001 | no eviction of exempt; Notice at most daily |
| Low disk space, image skipped | STO-LIM-002 | skip image ingest; Notice |
| Retention or budget sweep removed rows | STO-POL-001 | Info, counts logged |
| Text, image over ceiling; rich dropped; 500+ members | CAP-LIM-001/002/003, SSP-LIM-001, SHF-LIM-001 | per FR-007-06 |
| Undecodable image | CAP-VAL-001, SSP-VAL-001 | skipped |

## 7. Acceptance Criteria
- **AC-007-01** (FR-007-01,02) Given a first launch, then the data folder exists with mode 0700 and contains `flotsam.sqlite`, `blobs/`, `thumbs/`; `PRAGMA journal_mode` returns `wal` and `PRAGMA foreign_keys` returns 1; making the parent unwritable before launch raises `STO-IO-002` and the alert offers exactly "Reveal Data Folder" and "Quit".
- **AC-007-02** (FR-007-03) Given the schema, then a unit test asserts every table and column in FR-007-03 exists, the `trigger` and the `hotkeyCode`+`hotkeyModifiers` unique indexes reject duplicates (trigger case-insensitively), `contentKey` is not unique, and deleting an item removes its representations, members and tag links but not its tags.
- **AC-007-03** (FR-007-04) Given the process is killed after a blob is renamed into place and before commit, when the app restarts and reconcile runs, then the orphan blob (older than 10 minutes) is deleted and `STO-IO-003` is logged; given a transaction that fails, then no new blob remains.
- **AC-007-04** (FR-007-05) Given the same text payload submitted twice concurrently, then exactly one item exists with `copyCount` 2; given a payload whose `contentKey` matches an item pinned 60 days ago, then no item is created and that item's `lastCopiedAt` is now; given a forced write failure during capture, then no blob remains and exactly one Notice `CAP-IO-001` appears.
- **AC-007-05** (FR-007-06) Given text of 10 MiB + 1 byte, an rtf of 5 MiB + 1 byte with plain text, an image of 100 MiB + 1 byte, and a 501-file copy, then the results are skipped with `CAP-LIM-001`, rich dropped with `CAP-LIM-002`, skipped with `CAP-LIM-001`, and 500 members with `CAP-LIM-003`; each at the exact limit is accepted.
- **AC-007-06** (FR-007-07) Given a TIFF screenshot copied, then a lossless PNG is stored, its `contentKey` equals the hash of the original TIFF bytes, `pixelWidth`/`pixelHeight` equal the stored PNG's dimensions, and a 256 px thumbnail appears within 1 s; deleting the thumbnail file causes it to be regenerated on next display without an error.
- **AC-007-07** (FR-007-08) Given a 5120 x 2880 opaque PNG and preset Efficient, then the stored image is 2560 x 1440 JPEG and `pixelWidth`/`pixelHeight` are 2560 and 1440; given an opaque 1000 x 500 PNG and preset Efficient, then it is stored as a JPEG of 1000 x 500, and with transparency it stays PNG; with Balanced it is 3840 px wide; with Original it is byte-identical to the source; an existing item is never changed by changing the preset. Given a 500 MiB budget and 600 MiB of unpinned images, then after ingest the total is at most 450 MiB and the oldest were removed first; given 600 MiB of pinned images alone, then nothing is deleted and one `STO-LIM-001` Notice appears, a second within 24 h does not.
- **AC-007-08** (FR-007-09,10) Given retention 30 days and items last copied 31 days ago (plain, pinned, with a trigger, with a hotkey), then after a sweep only the plain item is gone; given an item copied 40 days ago and pinned for a year, when it is unpinned, then it survives sweeps for 24 hours and is deleted by the first sweep after that; given retention is lowered from Forever to 7 days, then a confirmation shows the exact count and cancel changes nothing.
- **AC-007-09** (FR-007-11) Given 50 items of which 3 are pinned and 2 have triggers, when Clear History > All time is confirmed without the option, then 45 are removed and 5 remain; with the option, 0 remain; tags remain in both cases; the database file after `wal_checkpoint` does not contain a unique marker string that was in a deleted item (checked by byte search of `flotsam.sqlite*`); a screenshot cleared is not re-imported at the next launch. Given no item is in the chosen range, then the preview count is 0 (Delete disabled, "Nothing to clear in this range.") and nothing is deleted.

## 9. Assumptions and open items (flagged for Friday)
1. Spike S-1 (FR-007-18): FTS5 trigram versus in-memory scan. The system SQLite on macOS 14 may predate trigram options; the requirement is the p95, not the technique.
2. Image quality presets and budget values are the architect's reading of "image budget plus Efficient downscale preset": three quality presets and four budgets as listed. Ryan may want fewer.
3. Clear history range choices (hour, 24 h, all) were added beyond the PRD's bare "Clear history", to serve the "copied a secret by mistake" case. Destructive class: flagged, no safety envelope widened (confirmation always, exempt items kept by default).
4. Paused persists across relaunch and also pauses screenshot pickup (the PRD does not say). Resume does not backfill.
5. Thumbnails are excluded from backups; the database and blobs are not (the user's backup policy decides). Time Machine therefore holds clip history; stated in README, not enforced.
6. `exemptReleasedAt` 24 h grace is a storage-layer rule not requested in the PRD; it prevents an unpin from deleting a year-old item at the next hourly sweep.
7. No database encryption at rest (FileVault is the boundary); stated in the PRD §9 privacy section as is.

## 10. Out of Scope
Sync, export, import or backup of the library (A1: sync is CUT; export deferred, not logged as a feature); encryption beyond FileVault; per-kind or per-app retention rules; compressing text; deduplicating blob bytes across items; cloud or network storage of any kind (A1, A4); OCR indexing of images (A3); deleting or moving the user's original files.
