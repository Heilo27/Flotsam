# FRD-007 — Retention and Storage

**Status:** Draft · 2026-11-16 · Constitution: [TRUTHS.md](../TRUTHS.md) · PRD: [PRD.md](../PRD.md) (feature F7) · Errors: [FRD-000](FRD-000-ErrorSystem.md)
**Owns:** the data folder, the SQLite schema (single definition), the blob store, the ingest pipeline and its limits, the image pipeline and thumbnails, retention and image-budget eviction, retention exemptions, Clear history, capture modes, integrity and recovery, deletion, the search index and query layer, migrations.
**Does not own:** what is captured and how it is classified or deduplicated ([FRD-001](FRD-001-Capture.md) FR-001-05 to -15); screenshot detection ([FRD-002](FRD-002-ScreenshotPickup.md)); panel behaviour ([FRD-003](FRD-003-Library.md)); the meaning of pin, tag, note, edit ([FRD-004](FRD-004-Organize.md)); hotkey and trigger grammar ([FRD-005](FRD-005-ShortcutsTriggers.md)); settings screens and the settings registry ([FRD-008](FRD-008-OnboardingSettings.md)); error catalogue ([FRD-000](FRD-000-ErrorSystem.md)).

## Truth Test
- Serves: P1 — "anything you copied or screenshotted in the past 30 days is back": the default retention is 30 days and nothing inside it is evicted by default (image budget aside, FR-007-08); the store is local-only, so "none of it ever leaves the Mac" holds by construction (no network code exists in this module).
- Supports: S2 — bundles and screenshots are stored as first-class items (bundle members, owned screenshot copies). S4 — items with a hotkey or trigger are exempt from retention, so saved snippets never expire.
- Violates: none. Storage is local files only (A1: no sync, no account); no telemetry or usage counters leave the device (A4). `pasteCount`, `copyCount` and `lastUsedAt` are local sort and display fields only.
- Verdict: KEEP. Capture modes (Paused, Curated) and Clear history are included because they serve the "none of it ever leaves / you control what is kept" half of P1 for a tool that records everything copied; Curated mode is the smallest feature that makes the tool usable by people who will not accept automatic capture. Both are small and cuttable without touching any other FRD's core path.

## 1. Purpose
Persist every item durably and cheaply, keep the library inside the user's chosen age and disk limits without ever deleting something the user has marked as valuable, and make deleting things truly delete them.

## 2. User Stories
- As a user, I copy something and it is safely in history even if the app is killed a second later.
- As a user, I keep 30 days by default and can change it to 7 days, 90 days, 1 year or forever.
- As a user, items I pinned or gave a shortcut never disappear on their own.
- As a screenshot-heavy user, I cap image storage so history cannot fill my disk, and choose to store smaller copies of large screenshots.
- As a user who just copied a secret by mistake, I clear the last hour of history and it is really gone.
- As a privacy-minded user, I pause capture before a sensitive task, or only save clips I explicitly choose.
- As a user, if the database is damaged or a migration fails, I am told plainly and my data is never silently destroyed.

## 3. Functional Requirements

**Folder, database, schema**
- **FR-007-01** Data folder. All persistent data lives under `~/Library/Application Support/Flotsam/`, created on first launch with permissions `0700` (files `0600`). Layout: `flotsam.sqlite` (with `-wal` and `-shm`), `blobs/` (original representation files), `thumbs/` (derived thumbnails, regenerable, excluded from backups), `tmp/` (in-flight writes, emptied at launch), `corrupt-<timestamp>/` (FR-007-13), `pre-migration/` (FR-007-17). Settings are not stored here (they live in the settings registry, FRD-008). The app never writes outside this folder except: pasteboard writes, Finder drag-outs, and the diagnostics copy. Failure to create or open the folder → `STO-IO-002` (Fatal). A runtime write failure to it → `STO-IO-001`. The modes are enforced on every launch, not only at creation: the folder and each Flotsam subfolder (`blobs/`, `thumbs/`, `tmp/`, `pre-migration/`, `corrupt-<timestamp>/`) are set to `0700` if they are anything else, and an existing `flotsam.sqlite`, `-wal` and `-shm` are set to `0600`. A symbolic link is never followed: a link where one of these should be is skipped, so its target's mode is not changed. A new `flotsam.sqlite` is created empty with `0600` before SQLite first opens it, so it and the `-wal` and `-shm` files SQLite derives from its mode are never readable by other users, not even briefly. A mode that cannot be set → `STO-IO-002` (Fatal): the app does not run on a readable database. A Debug build may be pointed at another folder with `FLOTSAM_DATA_DIR` for isolated test launches (docs/AGENT-LAUNCH.md); a Release build ignores it, and a Debug launch with it set to this real folder, or to a folder inside it, is refused.
- **FR-007-02** Database configuration. One SQLite database, WAL journal, `synchronous=NORMAL`, `foreign_keys=ON`, `secure_delete=ON`, `busy_timeout` 5 s on every connection the open makes, the read-only integrity probe of FR-007-13 included: a lock held when the open starts (for example the last connection of a previous instance closing and cleaning up the `-wal`) is waited out for up to 5 s and does not fail the open; only a lock still held after that fails it with `STO-DB-003` (Fatal), and a busy file is never treated as damaged or quarantined. Exactly one serial writer; any number of concurrent readers. All writes are transactions (FRD-004 FR-004-14 builds on this). Reads from the main thread are never performed. The SQLite binding library is an architecture decision (ADR), not a requirement; whichever is chosen is the only module that imports SQLite, and no SQLite type crosses its API (FR-000-02).
- **FR-007-03** Schema (single definition; other FRDs name fields, this FRD owns their storage). Times are UTC milliseconds since epoch.
  - `item`: `id` (UUID text, primary key); `kind` (FRD-001 FR-001-08 enumeration); `createdAt`; `lastCopiedAt` (sort key for Recent); `copyCount` (default 1; incremented by dedupe bumps); `pasteCount` (default 0); `lastUsedAt` (null until first paste or drag-out); `contentKey` (FRD-001 FR-001-15; indexed, not unique, because FRD-004 FR-004-08 allows duplicates after an edit); `plainText` (null for non-text kinds); `searchText` (FR-007-18); `sourceBundleId` (null for "Another device" and Unknown), `sourceName`; `byteSize` (sum of stored representation sizes, excluding thumbnails); `pixelWidth`, `pixelHeight` (images and screenshots); `originalPath` (screenshots only; FRD-002 FR-002-09); `pinned` (default 0); `note` (null or ≤ 2,000 characters); `updatedAt`; `hotkeyCode`, `hotkeyModifiers` (both null when none; unique index on the pair where not null); `trigger` (null when none; unique index, case-insensitive collation, where not null); `exemptReleasedAt` (FR-007-10); `isSecure` (0 or 1, default 0) and `secureCiphertext` (blob, null unless secure; schema version 2); `name` (text, null or 1 to 100 characters; set only on a `bundle` by FRD-004 FR-004-42; schema version 3); `ocrText` (null, or 1 to 10,000 characters of text recognised in an `image` or `screenshot`; never on a secure row; schema version 4) and `ocrAt` (null until recognition has been attempted, then the time of the attempt; FR-007-23). A secure item (FRD-001 FR-001-25) is a text item whose `isSecure` is 1: `secureCiphertext` holds the AES-GCM sealed text (at most 64 KB, key in the Keychain, never in the database), `plainText` and `searchText` carry nothing of its content, `contentKey` is `secure:` plus a keyed fingerprint (never a bare hash of the text), and it has no representation, no thumbnail and no blob. The database enforces the invariant with triggers on insert and update: a secure row has a ciphertext, no plain text, no hotkey and no trigger, and a write that breaks any of these fails.
  - `representation`: `id`, `itemId` (cascade delete), `uti` (e.g. `public.rtf`), `byteSize`, `blobName`. Plain text is never a representation (it is `item.plainText`); rich text and image bytes are always files in the blob store, so the database stays small.
  - `bundleMember`: `itemId` (cascade), `ordinal`, `path`, `bookmark` (blob), `isDirectory`. Files are stored by reference only (FRD-001 FR-001-12).
  - `tag`: `id`, `name` (unique, case-insensitive), `color`, `createdAt`. `itemTag`: `itemId`, `tagId` (both cascade; unique pair). Deleting an item removes its `itemTag` rows; deleting all items never deletes tags.
  - `meta`: `key` (primary key), `value`. Keys: `schemaVersion`, `screenshots.lastScanAt` (FRD-002 FR-002-08), `retention.lastSweepAt`, `budget.lastNoticeAt`.
  - An item is **exempt** (FR-007-10) when `pinned = 1` or `trigger` is not null or `hotkeyCode` is not null. This is derived, never stored as a second flag.
- **FR-007-04** Blob store. A representation file is `blobs/<first two characters of itemId>/<itemId>.<n>`. A blob is written to `tmp/`, flushed, and atomically renamed before the database transaction that references it begins; if the transaction fails the blob is removed. A blob is never modified in place. A file written over an existing one (a regenerated thumbnail) replaces it with one rename, so a reader sees the old file or the new one and never a moment with neither. Files are removed only after the transaction that unreferences them commits. A crash between blob write and commit leaves an orphan blob that FR-007-13 reconciles. No blob is ever shared between items.

**Ingest**
- **FR-007-05** Ingest pipeline (the only way an item is created or bumped). Input: an immutable value from capture (`CapturedPayload`, FRD-001 FR-001-17), screenshot import (FRD-002 FR-002-09; supplies `createdAt`, `lastCopiedAt`, `originalPath`) or a Shelf drop (FRD-006 FR-006-13). It runs on one serial background actor, in this order: (1) inside one write transaction look up `contentKey`; a match bumps the existing item (`lastCopiedAt` = now, or the supplied date for screenshots but never moving it backwards; `copyCount` + 1) and returns `bumped(id)` with nothing else changed. A bump never raises a limit notice: re-copying a payload that was already ingested (including one whose over-ceiling parts were skipped or dropped the first time, FR-007-06) bumps the existing item and raises no new notice, whether the match is found at step 1 or at the re-check in step 6 when two identical payloads arrive together. The notice belongs to the copy that created the item. (2) Otherwise apply limits (FR-007-06). (3) Disk guard (FR-007-14). (4) For images, the image pipeline (FR-007-07). (5) Write blobs (FR-007-04). (6) Insert `item`, `representation`, `bundleMember` and `searchText` in the same transaction as step 1 (so two identical payloads arriving together create one item). (7) After commit, publish an `itemsChanged` event (Library, Shelf and counts refresh; FRD-004 FR-004-13), enqueue thumbnail work, and run the budget check (FR-007-08). Result: `Result<IngestOutcome, FlotsamError>` where `IngestOutcome` is `created(id)` or `bumped(id)`. Ingest is idempotent per payload: a copy that loses that race never reports a failure (limits, disk guard, image decode or blob write) for a payload the other copy already stored, so before returning a failure from steps 2 to 5 it looks `contentKey` up again, and a match is `bumped(id)` exactly as in step 1 (no notice, no blob left behind) while no match returns the original failure. A database or disk failure rolls back everything, removes new blobs, and returns the `STO-*` code; capture surfaces it as `CAP-IO-001` with the `STO-*` code as underlying error (one Notice, not two); screenshot import and Shelf drop surface the `STO-*` code per FRD-002 and FRD-006.
- **FR-007-06** Ingest limits (single definition of every ceiling). Plain text: 10 MiB of UTF-8. Each rich representation (`public.rtf`, `public.html`): 5 MiB. Image: 100 MiB of source bytes. Bundle: 500 members (extra members dropped, `CAP-LIM-003` carrying the true member count; this is the only place the ceiling is applied and the code raised). Breaches: plain text or image → the item is skipped (`CAP-LIM-001`, `SSP-LIM-001`, `SHF-LIM-001` by source); a rich representation → dropped alone and plain text kept (`CAP-LIM-002`). `{limit}` in messages is the ceiling formatted with binary units (for example "10 MB"). The ceilings are constants in one place in the code and are not user-settable.
- **FR-007-07** Image pipeline. Decoding and downscaling use ImageIO only, off the main thread, with one image in flight. Steps: (1) decode metadata; undecodable → `CAP-VAL-001` or `SSP-VAL-001` by source; (2) decode the pixel size; (3) TIFF is converted to lossless PNG; PNG and JPEG are otherwise stored as received; (4) apply the image quality preset (FR-007-08): `Balanced` and `Efficient` downscale, `Efficient` also converts opaque images to JPEG, `Original` stores as received; (5) store, and record `pixelWidth` and `pixelHeight` as the dimensions of the stored blob after any downscale (the copied original's size is not kept); (6) generate a thumbnail asynchronously: longest edge 256 px (512 px for the Library preview pane), JPEG quality 0.8, written to `thumbs/<itemId>-<size>.jpg`; generating one at ingest writes the file only and never fills the memory cache, which fills only when a panel displays a thumbnail. A missing or corrupt thumbnail is regenerated on demand and never an error. `contentKey` always comes from the raw received bytes before any conversion or downscale (FRD-001 FR-001-15), so dedupe is unaffected by the preset. The in-memory thumbnail cache is capped at 64 MB (least recently used), is emptied when the last panel closes (FRD-003 FR-003-13; target state, wired by TASK-383) and is shared by the Library (FRD-003 FR-003-13) and the Shelf (FRD-006 FR-006-07).
- **FR-007-08** Image budget and quality (settings keys `storage.imageBudget`, `storage.imageQuality`; registry in FRD-008). The budget counts the `byteSize` of stored image and screenshot representations only (not thumbnails, text, or files held by reference). Budget values: 500 MiB, 2 GiB (default), 10 GiB, Unlimited. Quality presets: **Original** (default; stored as received, TIFF as PNG), **Balanced** (longest edge above 3840 px is downscaled to 3840 px), **Efficient** (longest edge above 2560 px is downscaled to 2560 px). A downscaled image keeps its format, except an opaque PNG or TIFF that was downscaled is re-encoded as JPEG quality 0.85. Under **Efficient** every opaque PNG or TIFF is stored as JPEG quality 0.85 whether or not it needed downscaling; an image with transparency stays PNG under every preset (a TIFF becomes PNG first, then this rule applies); a JPEG is re-encoded only when downscaled. The preset applies to new items only; existing items are never re-encoded. Enforcement: after each image ingest and in each retention sweep (FR-007-09), if the total exceeds the budget, non-exempt image and screenshot items are deleted oldest `lastCopiedAt` first until the total is at or below 90 % of the budget; the item just ingested is not evicted in its own pass. Eviction honours the same 24 h `exemptReleasedAt` grace as the time sweep (FR-007-09, FR-007-10): an item un-pinned (or stripped of its last trigger or hotkey) less than 24 h ago is not evicted yet. If exempt items (including those inside the grace) alone exceed the budget, nothing exempt is evicted and `STO-LIM-001` is raised as a Notice, at most once per 24 h (`budget.lastNoticeAt`). Lowering the budget triggers the budget confirmation in FR-007-09 (its own string, with count and size). Evictions are logged as `STO-POL-001` (counts only).

**Retention**
- **FR-007-09** Retention presets and sweep (key `storage.retention`). Values: 7 days, 30 days (default), 90 days, 1 year, Forever. An item is eligible for retention deletion when it is not exempt (FR-007-10), `lastCopiedAt` is older than the preset (so re-copying an old item renews it), and `exemptReleasedAt` is null or older than 24 h. The sweep runs 30 s after launch, then every hour, and on wake from sleep; it deletes in batches of at most 500 items per transaction (so the writer is never held for more than 50 ms), through the deletion operation (FR-007-15), measured by one `retention.sweep` signpost interval covering the whole sweep, with each batch an event inside that interval. A sweep that removed rows logs `STO-POL-001` (counts only, no content) and does not raise a Notice. Changing to a shorter preset first shows a confirmation with the exact number of items that would be deleted (`storage.confirm.shorten`: "This permanently deletes {n} items older than {period}. Pinned items and items with a shortcut are kept."). Lowering the image budget has its own confirmation (`storage.confirm.lowerBudget`: "Lowering the image budget removes {count} older images ({size}). Pinned and shortcut items are kept."), not the shorten string. The core returns the count and stored size (`retentionPreview`, `imageBudgetEvictionPreview`); the strings live in the UI layer (FRD-008). When the count is 0 no confirmation is shown and the setting is applied directly. Cancel reverts the control; the sweep for the new value runs only after confirmation. Changing to a longer preset deletes nothing. Forever disables the time sweep only; the image budget still applies.
- **FR-007-10** Retention exemptions (single definition). An item with `pinned = 1`, or a trigger, or a hotkey is exempt from: the time sweep (FR-007-09), the budget eviction (FR-007-08) and Clear history (FR-007-11) unless its explicit "also delete pinned and shortcut items" option is chosen. It is never exempt from an explicit delete by the user (FRD-004 FR-004-09). When the last exemption is removed (unpin, remove trigger, remove hotkey), `exemptReleasedAt` is set to now, so a long-pinned old item is not deleted within 24 h of unpinning; it is cleared whenever an exemption is set again. The grace protects against the automatic passes (time sweep and budget eviction); Clear history (FR-007-11) honours only exemption itself, because it is the user's explicit, counted action. Exemption does not apply to files on disk: files held by reference are outside Flotsam's control.
- **FR-007-11** Clear history. Settings › Storage › "Clear History…" opens a sheet with a range (Last 5 Minutes, Last Hour, Last 24 Hours, All Time) and an unchecked option "Also delete pinned and shortcut items". It shows the exact count to be deleted and a destructive "Delete Items" button (the count is stated in the sheet text above the button, not on it, so the label stays within the 15-character button limit; `storage.confirm.clear`: "This permanently deletes {n} items. This can't be undone."). The count always belongs to the range and option on screen: until the count for the current choice has loaded (when the sheet opens and after each change of range or option) the secondary text reads "Counting items…" and Delete is disabled. Every change counts afresh (returning to an earlier choice does not reuse its old count), and a count that arrives late for an earlier choice is discarded, so the user never confirms one count and deletes another. If the count cannot be read, the failure is reported like any other storage error, the secondary text reads "Couldn’t count the items in this range." and Delete stays disabled; it is never shown as an empty range. When no item is in the range (count 0) the Delete button is disabled and the secondary text reads "Nothing to clear in this range."; nothing is deleted and there is no confirmation. The core returns the count and stored size (`clearHistoryPreview`) and the number actually deleted; the strings live in the UI layer (FRD-008). Deletion uses FR-007-15 over items whose `lastCopiedAt` is inside the range, minus exempt items unless the option is checked. Tags are kept. `screenshots.lastScanAt` is not reset, so cleared screenshots are not re-imported. After the transaction the database is checkpointed (`wal_checkpoint(TRUNCATE)`) and its free pages released (`incremental_vacuum`) so deleted content is not left in the file; with `secure_delete` on (FR-007-02) deleted pages are overwritten. Clear history never touches files held by reference or screenshot originals on disk. A progress state is shown for more than 1 s of work. The result is announced with a HUD "{n} items deleted". Deleted content also survives in the full plaintext database copies beside the live file, so when Clear history deletes at least one item it also removes every pre-migration copy (FR-007-17) and every corrupt-database quarantine (FR-007-13), whatever range was chosen: a copy made earlier may hold an item cleared from the last hour, so no range can be shown safe to skip. Only regular files Flotsam names are removed from `pre-migration/`, and only real folders Flotsam names are removed as quarantines (the rules in those requirements); a copy that cannot be removed is logged `STO-IO-003` with a count, the clear itself still succeeds, and the outcome reports the purge as incomplete so the UI can say that copies remain. This is deliberate loss of recovery copies (the rollback for the last migration and the evidence of a damaged database); it is part of what "permanently deletes" means.
  - **Clear Recent (menu bar).** The menu-bar menu offers a "Clear Recent" submenu with two ranges, Last 5 Minutes and Last Hour (FR-008-16). It is the same operation as the sheet above, not a second one: it uses the same range selection, count, deletion path (FR-007-15), scrub, HUD and error reporting, with the option "Also delete pinned and shortcut items" always off. Choosing a range never deletes by itself: the menu asks for confirmation in an alert that names the range and shows the exact count ("This permanently deletes {n} items. This can't be undone.") with a destructive "Delete Items" button and Cancel. If the count is 0 nothing is asked and the HUD reads "Nothing to clear in this range."; if the count cannot be read the failure is reported and nothing is deleted. What it deletes: every non-exempt item (not pinned, no trigger, no hotkey) whose `lastCopiedAt` is inside the range, their stored representations and thumbnails, and, because at least one item was deleted, every pre-migration database copy and corrupt-database quarantine exactly as the sheet does (this is the same deliberate loss of recovery copies). It never deletes pinned or shortcut items, tags, files held by reference, or screenshot originals on disk.

**Capture modes**
- **FR-007-12** Capture modes (key `capture.mode`, persisted across launches): **Active** (default), **Paused**, **Curated**. Paused: nothing is captured or saved automatically, including screenshot pickup (the pickup advances `screenshots.lastScanAt` without importing, so screenshots taken during a pause are not imported on resume). Curated: nothing is saved unless the user runs Save Clipboard (FRD-005 FR-005-06) or drops onto the Shelf (FRD-006 FR-006-13); screenshot pickup behaves as in Paused. Active resumes all capture. Save Clipboard and Shelf drops work in every mode. While Paused the clipboard poll does not run and the shared timer slows (FRD-001 FR-001-19); resuming re-baselines the pasteboard at the moment the mode changes, so nothing copied during the pause is captured even by a check that runs right after the change. Changing mode takes effect at once (the poll resumes with an immediate check, FRD-001 FR-001-19), never discards held clipboard state, and is shown at all times by the menu-bar icon (FRD-008). The mode is changed from the menu bar ("Pause Capture" / "Resume Capture") and from Settings › Storage; Curated is chosen in Settings only. The menu item reads "Pause Capture" only in Active (and pauses); in Paused and in Curated it reads "Resume Capture" (and returns to Active), as FRD-008 FR-008-16 states; the menu never produces Curated. Paused persists across relaunch, because forgetting to resume would silently lose history only if no indicator existed; the icon state and the menu label are that indicator.
  - **Timed pause.** While Active, the menu's "Pause For" submenu (FR-008-16) offers 15 Minutes, 1 Hour and Until Tomorrow. Choosing one sets the mode to Paused and records when the pause ends: 15 or 60 minutes from the choice, or the next local midnight. When that moment arrives the mode returns to Active exactly as Resume Capture does (immediate re-baselined check, nothing copied during the pause is captured), and the menu-bar icon follows the mode (FR-008-16). Leaving Paused by hand before then (Resume Capture, or Curated in Settings) cancels the timed end. The end is stored (key `capture.pauseUntil`, UTC milliseconds; state, not a registry preference, FR-008-01), so quitting during a timed pause does not make it indefinite: at the next launch an end already in the past resumes at once and one still ahead is timed again; a Mac that sleeps through the end resumes at wake. A timed pause uses one one-shot timer that exists only while an end is pending (ADR-0004); nothing polls for it, and a plain Pause Capture (no end) has no timer.

**Reliability**
- **FR-007-13** Integrity and recovery. At launch, before the database is opened for writing (so before any migration, journal-mode change or vacuum), run `PRAGMA quick_check` off the main thread on a read-only connection; after migration, run it again on the migrated file, and log that result after the migrate entry (FRD-000 logging). On failure, or when SQLite reports the file is damaged or not a database: move `flotsam.sqlite*` and `blobs/` into `corrupt-<timestamp>/`, create a fresh database, raise `STO-DB-002` (Notice with "Reveal Data Folder" in the Notice detail, FRD-008), and never delete the moved data except as this requirement states: the quarantine is kept for recovery for 30 days counted from the timestamp in its name, and is deleted whole at a later launch once it is older than that (the launch check in FR-007-17), or at once by Clear history (FR-007-11). Only a real folder named exactly `corrupt-<digits>` is ever judged; a link, a file or any other name is left alone. The moved database and its `-wal` file are preserved byte-for-byte as they were found: nothing writes to a damaged file before it is set aside, so the quarantine copy is exactly what the user had and can be handed to a recovery tool. The `-shm` file moves with them; it is SQLite's rebuildable index of the `-wal`, which SQLite updates on every open, so its bytes are not guaranteed. The pre-open check never writes to the file: a database in WAL mode with no `-shm` beside it (the normal state after a clean shutdown, or a file restored or copied alone) cannot be opened read-only, so the check runs on a private copy of the file and its `-wal` in `tmp/`, which is removed afterwards; such a healthy file opens normally and a damaged one is quarantined as above. The check is structural only (`quick_check`): constraint violations are not caught at open. A zero-byte `flotsam.sqlite` with no `-wal`, or with an empty one, is a new empty library, not damage. A zero-byte `flotsam.sqlite` beside a non-empty `-wal` is damage: SQLite deletes the `-wal` of an empty database when it opens it, which would destroy committed data, so before any open the zero-byte file, the `-wal` and the `-shm` are moved byte-for-byte into `corrupt-<timestamp>/` (with `blobs/`, as for any damaged file), a new empty library is created and `STO-DB-002` is raised. If moving the files aside fails partway (for example only the `-shm` cannot move), that launch fails closed with `STO-DB-003` and what already moved stays in its `corrupt-<timestamp>/`, which is marked `notice-pending`; the next launch that opens raises `STO-DB-002` once and removes every such marker, whether or not that launch itself quarantined, even when it finds nothing left to quarantine. The user is told in that case, not always: if the marker itself cannot be written, the relaunch is silent after the `STO-DB-003`; and a marked quarantine already older than 30 days is deleted whole with its marker before the marker is read, so that launch raises no notice for it, but only on a launch that runs no migration (the expiry rule of FR-007-17: the schema version is the same before and after and the integrity check passes). On a launch that migrates, or that quarantines (its new library counts as migrated), the 30-day expiry does not run: the marker is read and removed and the notice is raised as usual. A damaged file written by a newer app version is quarantined, not refused, so the data is preserved. If the check on the migrated file fails, the file is quarantined like any other damaged one; the migration has already written to it, so that copy is not the bytes the user had (it is a migration bug, not user damage). Reconcile (at launch, and weekly): (a) a blob file with no representation row and older than 10 minutes is deleted; (b) a representation row whose blob is missing is removed, and if the item then has no plain text, no remaining representation and is not a files kind (file, folder or bundle), the item is removed through the single deletion path (FR-007-15); each repair logs `STO-IO-003` with ids and counts only. A thumbnail with no item is deleted silently. Only files named as Flotsam names its blobs and thumbnails are ever judged orphans; anything else in `blobs/` or `thumbs/` is left alone. If any part of `blobs/` cannot be read (a folder cannot be listed, or a listed file cannot be inspected), the missing-blob repair (b) is skipped for that run and a file that cannot be inspected is never judged an orphan, so an unreadable folder can never empty the library. Reconcile runs off the main thread, 15 s after launch and then every 7 days, and never blocks the UI.
- **FR-007-14** Disk guard. Before writing any blob, if available capacity (`volumeAvailableCapacityForImportantUsage`) is below 500 MiB, image ingest is skipped with `STO-LIM-002` (Notice, throttled by FR-000-08); text and files still ingest until capacity is below 50 MiB, after which every ingest fails with `STO-IO-001`. SQLite "disk full" on write is `STO-DB-001`.
- **FR-007-15** Deletion (the only deletion path: user delete, retention, budget, Clear history, ungroup's bundle removal, `LIB-IO-001`, Shelf and Library delete). `delete(ids)` runs one transaction that removes the item rows and, by cascade, representations, bundle members and tag links; after commit it removes blob files and thumbnails, evicts the thumbnail cache entries, and publishes `itemsDeleted(ids)` synchronously so the hotkey registry and trigger snapshot drop the item before the call returns (FRD-005 FR-005-22). Thumbnail writes (ingest warm-up and regeneration) re-check that the item still exists in the same uninterrupted step that writes the file and fills the cache, and the delete's thumbnail removal and cache eviction run in that same serial step, so a render still in flight when a delete commits can never put a thumbnail back: after `delete(ids)` returns, no thumbnail file or cache entry for a deleted item exists, now or later. A blob that cannot be removed after commit is left for reconcile and logged as `STO-IO-003`; the delete itself still succeeds. A failed transaction deletes nothing (`STO-DB-001`). `delete(ids)` is unconditional: an explicit user delete is never refused for exemption, and FRD-003 decides whether a failed item is deleted. The automatic passes (time sweep, budget eviction, Clear history) choose their ids in a read, so their delete re-applies the selection predicate, including exemption, inside the same transaction: an item pinned, given a trigger or hotkey, or copied again since the read is skipped, never deleted. Deletion never touches a file referenced by a `file`, `folder` or `bundle` item, nor a screenshot's original.
- **FR-007-16** Performance. Measured in a release build against a 10,000-item database with 2,000 images: database open and schema check ≤ 300 ms; persist and queryable, thumbnail excluded, per FRD-001 FR-001-20 (`capture.persist`); one retention batch holds the writer ≤ 50 ms p95 (`retention.sweep`); Clear history of 10,000 items completes ≤ 5 s (`retention.clearHistory`: one interval covering the count, every delete batch and the database scrub); physical footprint (`phys_footprint`, as reported by `footprint`) including a full thumbnail cache stays under the 150 MB budget set in the PRD.
- **FR-007-17** Migrations. `PRAGMA user_version` is the schema version (mirrored in `meta.schemaVersion`). Migrations are forward-only, numbered, and each runs in one transaction. Before any migration, a complete snapshot of `flotsam.sqlite` is written to `pre-migration/flotsam-v<from>.sqlite`: every row committed at that moment is in the copy, including rows still only in the `-wal` file, and the copy holds them whatever other connections are doing (an open reader never makes it incomplete). It is made with SQLite's online backup, built under `tmp/` with mode `0600` and moved into place only when whole; if it cannot be completed or put in place the launch aborts with `STO-DB-003` before any migration runs, no partial copy is left, and an earlier copy is not touched. Taking the copy never depends on a checkpoint of the `-wal` succeeding. (Only the latest copy is kept: older copies are deleted only if their names are exactly `flotsam-v<int>.sqlite` or `flotsam-v<int>-<int>.sqlite`, or either plus `-wal` or `-shm`, i.e. files Flotsam created; any other file in `pre-migration/` is never touched, and only regular files are ever removed: a folder, link or other special entry that merely carries one of those names is left alone). If a folder, link or other non-file entry already has the copy's name, the migration neither deletes it nor fails: the copy is written as `flotsam-v<from>-<n>.sqlite` with the lowest free `n` (1, 2, ...), and is then treated like any other copy for pruning, expiry and Clear history. A stale regular file with the name is replaced. A migration failure, or a database whose version is newer than the app understands, aborts startup with `STO-DB-003` (Fatal); the database is left untouched. Version 1 is the schema in FR-007-03 without the secure columns; version 2 adds `isSecure`, `secureCiphertext` and the invariant triggers, and existing rows take the defaults (not secure, no ciphertext), so there is nothing to backfill; version 3 adds the nullable `name` column, and existing rows take null, so there is nothing to backfill; version 4 adds the nullable `ocrText` and `ocrAt` columns and one partial index, nothing else, and rewrites no existing row (their `ocrAt` stays null, which is the recognition backlog, FR-007-23). A pre-migration copy is a full copy of the database (secure items in it are still ciphertext), and it still holds items the user has since deleted, so it is kept only until the migration is confirmed. The confirmation is a later launch that opens the database cleanly and runs no migration itself: the schema version is the same before and after, so it is the version the migration produced, and the integrity check (FR-007-13) passes on it. That launch deletes every pre-migration copy at once, however young: no waiting period. Each copy goes with its `-wal` and `-shm` files, again only regular files Flotsam names. Until a launch confirms, the copy stays: the launch that migrated deletes nothing (it cannot confirm its own migration), a launch that failed (`STO-DB-003`) or found the database damaged and quarantined it deletes nothing, and if the app quits or crashes anywhere between the migration and a confirming launch the copy is still there, because nothing deletes it but a confirming launch. A copy is also kept while a corrupt-database quarantine made after the copy was taken still stands (FR-007-13): the live library is then not the one the copy led to, and the copy may be the last good version of the data; it is deleted at the first confirming launch after that quarantine is gone. "After the copy" is judged by the copy's own date (the newer of its creation and modification times) against the quarantine's name stamp, so a copy dated in the future (a clock set ahead when it was taken) is deleted by a confirming launch even when a quarantine really came after it: this is the baseline the rule sets, and it deletes nothing beyond what the rule permits. A copy that cannot be inspected or removed is left for the next launch and never stops the launch. The privacy notes (README) say this in plain words. Clear history deletes the copies at once (FR-007-11).

**Search index and query layer**
- **FR-007-18** Query layer and search index. All reads go through one query layer that takes a filter (FRD-004 FR-004-10), search tokens (FRD-003 FR-003-09), and a sort (FRD-004 FR-004-12) and returns pages of 200 rows plus a count; sidebar counts are computed by the same filter semantics. `item.searchText` is a normalised (case-folded, diacritic-stripped) concatenation of the fields listed in FRD-003 FR-003-09 (plain text first 10,000 characters, link URL, note, a bundle's name, tag names, source name, the recognised text of an image or screenshot (`ocrText`, first 10,000 characters, FR-007-23), file and folder names of members, kind label, original file name), rewritten in the same transaction whenever any of them changes. The matching strategy (FTS5 trigram index versus an in-memory scan of `searchText`) is chosen by spike S-1 against FRD-003 FR-003-10 (p95 ≤ 100 ms at 10,000 items); whichever is chosen, results are exactly those defined by FR-003-09 (substring, AND over tokens). Until S-1 decides, the shipped strategy is the in-memory-style scan (`instr` over `searchText`, one AND per token), which already gives the FR-003-09 set; the public API is unchanged by the outcome. Rows carry the FR-003-07 primary line and the FR-003-07 missing-file state (checked against the disk after the read transaction ends, never stored), and the alphabetical sort (FR-004-12) orders by that same text, locale-aware, ties broken by `lastCopiedAt` descending then `id`; every other sort ends the same way so order is stable across loads. The source-app filter and the sidebar's app counts group by one key: bundle identifier, else the "Another device" bucket (stored source name `Another device`, FR-001-14), else Unknown (FR-001-13). A page and its count are read in one transaction. Database read failure → `STO-DB-004`.
- **FR-007-23** Image text for search (parity ticket TASK-552, 2026-11-19; truth A3 as amended: on-device recognition, search only). (a) Storage keeps `ocrText` and `ocrAt` on each `image` and `screenshot` item (FR-007-03). The recognised text, at most 10,000 characters, is folded into `searchText` (FR-007-18) in the same transaction that stores it, so search sees both or neither. `ocrAt` is set whenever an attempt finishes, including one that found no text or could not read the image, so an item is attempted once and never queued again. Recognition changes neither `lastCopiedAt` nor `updatedAt` and publishes no item event: it never reorders the Library and never triggers itself. (b) The text is read with Apple's Vision text recognition, entirely on this Mac, from the item's stored primary representation: no network, no cloud or third-party recogniser. (c) Scheduling (truth S5, ADR-0004): no timer and no poll. A pass runs when the database opens and when an item event arrives; it reads the newest 12 items with `ocrAt` null, one at a time, at background priority, and stops. A library with a larger backlog (every existing image after upgrading to schema version 4) drains over later launches and ingests; nothing wakes the app to finish it. A pass already running is not doubled: one more follows it. (d) A secure item (FRD-001 FR-001-25) is never read, and the database refuses `ocrText` on a secure row. (e) The recognised text is a column of the item row, so it is deleted with the item by FR-007-15 (user delete, retention, image budget, Clear history); no copy of it is kept elsewhere. (f) A blob that is missing or damaged, or an image the recogniser rejects, is reported to the log as `STO-IO-001` and never shown to the user (it happens in the background); the item is marked attempted. A failed write is reported as `STO-DB-001` and the item stays queued. (g) A3 limit: the text is for search only (FRD-003 FR-003-55). It is not shown, edited, exported, copied or put on a pasteboard or a drag.

## 4. Data Requirements
- Settings keys owned here (registry in FRD-008): `storage.retention` (enum, default `d30`), `storage.imageBudget` (enum, default `gib2`), `storage.imageQuality` (enum, default `original`), `capture.mode` (enum, default `active`). Also owned here, but state rather than a preference and so not in the registry: `capture.pauseUntil` (FR-007-12, the end of a timed pause).
- Persisted: everything in FR-007-03 and the blob store. Not persisted: thumbnail cache, query pages, ingest queue.
- Item counts, byte sizes of database and blobs, preset values are the only storage facts appearing in diagnostics (FR-000-14); never content.

## 5. Business Rules
- Retention age is measured from `lastCopiedAt`, not `createdAt`. A re-copy renews an item; opening, pasting or editing does not.
- Exempt means pinned, triggered or hotkeyed (FR-007-10). Only an explicit delete or the Clear history option removes an exempt item.
- Bytes of files held by reference are never counted and never deleted.
- Dedupe is global and age-independent (FRD-001 FR-001-15): a retention-deleted item does not block re-capture because it no longer exists.
- Every path that creates items goes through FR-007-05; every path that removes items goes through FR-007-15.
- Secure items follow the same retention as any other item (FR-007-09; age from `lastCopiedAt`, the user's setting, 30 days by default) and are exempt only when pinned. Delete, retention and Clear history remove the row and with it the ciphertext (`secure_delete` is on, FR-007-02). Reconcile (FR-007-13) never treats a secure row as empty for lacking plain text. A secure item whose key cannot be read stays in the library as an unavailable row; nothing about it is an error at launch.
- Nothing here makes a network call. The module has no networking imports.

## 9. Assumptions and open items (flagged for Friday)
1. Spike S-1 (FR-007-18): FTS5 trigram versus in-memory scan. The minimum OS is macOS 26, whose system SQLite is the one measured in ADR-0003; the requirement is the p95, not the technique.
2. Image quality presets and budget values are the architect's reading of "image budget plus Efficient downscale preset": three quality presets and four budgets as listed. Ryan may want fewer.
3. Clear history range choices (hour, 24 h, all) were added beyond the PRD's bare "Clear history", to serve the "copied a secret by mistake" case. Destructive class: flagged, no safety envelope widened (confirmation always, exempt items kept by default).
4. Paused persists across relaunch and also pauses screenshot pickup (the PRD does not say). Resume does not backfill.
5. Thumbnails are excluded from backups; the database and blobs are not (the user's backup policy decides). Time Machine therefore holds clip history; stated in README, not enforced.
6. `exemptReleasedAt` 24 h grace is a storage-layer rule not requested in the PRD; it prevents an unpin from deleting a year-old item at the next hourly sweep.
7. No database encryption at rest (FileVault is the boundary), except secure items, whose text is sealed individually (FRD-001 FR-001-25); stated in the PRD §9 privacy section.

## 10. Out of Scope
Sync, export, import or backup of the library (A1: sync is CUT; export deferred, not logged as a feature); encryption beyond FileVault; per-kind retention rules; per-app clip lifetime rules (v1.1, TASK-555); compressing text; deduplicating blob bytes across items; cloud or network storage of any kind (A1, A4); using recognised image text for anything but search, or showing, editing or exporting it (A3: on-device recognition for search is FR-007-23); deleting or moving the user's original files.
